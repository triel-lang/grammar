# Related Work

This file compares TRIEL with the closest languages and formalisations, on the basis of their published papers, documentation and specifications. The traditions TRIEL draws on, and the definitions and results each construct uses, are in [`FOUNDATIONS.md`](FOUNDATIONS.md). `TECHNICAL_REPORT.md` §3 compares TRIEL with OPA/Rego, Wysteria and Wys\*, ZK-SecreC, Allium, and ZoKrates and Noir. Statements about TRIEL here are limited to what the Isabelle/HOL core in [`formal/core`](formal/core/CORE.md) proves; names in code font are its definitions and theorems.

## Authorization policies for software and agents

**Cedar** [1] is a language for authorization policies. A request is allowed when some `permit` policy is satisfied and no `forbid` policy is; a satisfied `forbid` overrides, and the default is deny [2]. Reading an attribute that is absent raises an error, and a policy whose evaluation raises an error is skipped [2]. Cedar's validator rejects access to an optional attribute that is not guarded by a `has` test [2]. With the usual guard, `resource has a && …`, a `forbid` policy is not satisfied when `a` is absent. Either way, a prohibition whose condition reads a missing value does not apply, unless the author writes the guard so that absence counts against the request, for example `if context has a then … else true`, or declares the attribute required, so that a request without it is rejected. For validated policies, and requests and entities that conform to the schema, the validator is proved sound in Lean: evaluation does not raise such errors [1; §3.5 of the extended version, arXiv:2403.04651]. The documentation lists the errors that validation does not exclude, among them access to the attributes of an entity that is missing from the entities passed with the request [2]. It names the rule "skip on error" and discusses it against the alternative of denying on an error, which it rejects for safety: one erroneous policy would deny every request [2]. The behaviour above is therefore a documented choice of the language, completed by the author of the policy, not a defect.

TRIEL makes the opposite choice the default for prohibitions. Its conditions are evaluated in strong Kleene logic, and a monitor blocks a prohibited action unless the condition is known to be false (`blocks`). The core models the two other readings of an undefined condition: skipping it (`skip_allows`) and reading an absent operand as false (`eval_af`). For each, it proves that there is a condition and a state where the reading allows the action although some completion of the data makes the condition true (`skip_reading_unsound`, `absent_false_unsound`). For a condition without `PRESENT` and `DEFAULT`, when the fail-closed monitor allows an action, the condition is false in every completion (`monitor_sound_completions`). These theorems are about the readings as defined in the core, not about the implementation of any language. Cedar decides single requests; TRIEL also has obligations with deadlines, breach handlers and invariants over traces.

**Dogwood** [3] extends the `permit`/`forbid` model of Cedar to the history of an AI agent's actions, so that a policy can depend on what the agent has already done. TRIEL has the same aim for agents. Relative to Dogwood it also states obligations with deadlines and breach handlers and gives three-valued verdicts on finite prefixes; it monitors these obligations and does not enforce them. The decision pipeline of Dogwood's reference implementation is fail-closed: a failure to evaluate the temporal conditions, to build the context or to build the request denies [4, §6.2 and §7 of the formal specification]. A Cedar policy whose evaluation raises an error is skipped, as in Cedar; the Dogwood test `erroring_forbid_is_skipped_weakening_the_deny` [4] records this as deliberate.

**The running example in Cedar and Dogwood.** `artifact/comparison/` expresses the example `core_invoice_agent` in both languages, runs it with cedar-policy-cli 4.14.0 and dogwood 1.1.0, and records every output. Neither language expresses the obligation with its fallback or the notification, since both decide only when a request arrives. When the owner's approval is an optional request attribute and is absent:

- with the guard that the validator asks for, `context has … && …`, the policy validates, the `forbid` is not satisfied, and both tools allow the payment without an error;
- without a guard, both validators reject the policy; if it is run anyway, its evaluation raises an error, the policy is skipped, and both tools allow the payment and report the error;
- in Cedar, a `forbid` written to hold unless its condition is known to be false validates and denies the payment, as the TRIEL monitor blocks it; on every recorded request, including a payment approved while the quote is missing, which both allow, its decisions are those of the monitor (`cedar/invoice_failclosed.cedar`);
- in Cedar, declaring the attribute required makes a request without it fail to parse.

When the approval is an event in Dogwood's history instead, its absence denies the payment. The policy then reads a missing `Approve` event as no approval: the denial comes from writing the prohibition over events, not from a third truth value.

**XACML 3.0** [5] has four decisions: Permit, Deny, NotApplicable and Indeterminate, the last returned when the decision point is unable to evaluate the request, for example because an attribute is missing (§5.53). An attribute designator for a missing attribute evaluates to Indeterminate if the policy marks the attribute `MustBePresent`, and otherwise to an empty bag (§7.3.5), which the functions applied to it may still turn into Indeterminate (§A.3.10). An Indeterminate result records which effect the failed rule could have had (§7.10), and combining algorithms decide how it affects the final decision: deny-unless-permit never returns Indeterminate (Appendix C.6), and a deny-biased enforcement point denies on every decision but Permit (§7.2.2). A deployment of XACML can therefore choose to deny when a condition cannot be evaluated. In TRIEL, an undefined condition is a value of the logic with strong Kleene connectives, the rule for prohibitions is fixed (block unless known to be false), and the verdict is kept apart from enforcement: a breach is recorded only when the condition is true (`undefined_guard_blocks_not_breach`). An XACML obligation is an operation that the enforcement point performs in conjunction with enforcing a decision, and the enforcement point denies access unless it can discharge it (§1.1.1, §2.12); a TRIEL obligation is an action due within a window, with a verdict on the trace.

## Languages for rights, norms and contracts

**ODRL 2.2** [6] describes policies as permissions, prohibitions and duties with constraints, for the use of digital assets. **LegalRuleML 1.0** [7] is an XML vocabulary for legal norms, with deontic specifications and defeasible rules. TRIEL is a textual language; the terms of its formal core have a trace semantics whose properties are machine-checked.

**Symboleo** [8] is a specification language for legal contracts with obligations and powers, given a formal semantics. **CL** [9] is a contract language in a dynamic deontic logic: obligations, permissions and prohibitions apply to actions, and violations carry reparations. Logics of violations [10] describe chains of reparations, and defeasible deontic logic, with reasoners such as SPINdle [11], decides what is obligatory when norms conflict or have exceptions. TRIEL shares with these the view of a contract as norms over actions, with deadlines and reparations; it gives verdicts on traces and has no rules of inference between norms, no defeasibility and no priorities between norms.

**Catala** [12] is a programming language for computations prescribed by legislation, such as taxes and benefits, with exceptions structured as in default logic. TRIEL does not compute such amounts; it states norms and decides whether a trace of events satisfies them. In the formal core, arithmetic occurs only in the amount of a `PENALTY`.

**DCR graphs** [13] describe processes declaratively, by relations between events such as conditions and responses. TRIEL states norms over a trace of events rather than the process that produces it.

## Runtime verification and enforcement

LTL3 [14] gives verdicts on finite prefixes that are final once decided. The verdicts of TRIEL for `ALWAYS`, `EVENTUALLY` and `NEXT` are three-valued in the style of LTL3 and final once decided (`inv_final`), but correspondence with LTL3 is not proved. The TRIEL core treats missing data inside the language and proves the treatment in Isabelle/HOL. A condition is evaluated in strong Kleene logic over a partial state. For conditions whose atoms are equitone, which excludes `PRESENT` and `DEFAULT`, a definite value is the value in every completion of the data (`monitor_sound_completions`, `breach_certain_completions`) and a definite verdict of an invariant survives the arrival of data (`inv_data_mono`; for the conditions themselves, `verdict_stable`); for the same conditions, over a type of values with at least two elements, strong Kleene evaluation is the most defined sound compositional evaluation (`kleene_optimal`). The verdict and the enforcement decision are kept apart and related by theorems: a prohibition is breached only when its condition is true, the monitor blocks unless the condition is known to be false, and every breach is a blocked action (`breach_blocked`). The monitor is a function on traces that replaces a blocked action by a clock tick: a suppression automaton in the sense of edit automata [19], where Schneider's execution monitors [18] would halt the target; it is sound (`enforce_sound`) and, where the condition is defined, transparent (`enforce_transparent`), the two properties in which the correctness of an enforcer is usually stated [29]. Under `ON_STALE BLOCK`, a value older than its `MAX_AGE` counts as missing, and, for the same conditions, a definite value computed without it is not overturned when it is refreshed (`stale_safe`).

The idea is established in runtime verification, and the core is much smaller than its neighbours. Strong Kleene evaluation over incomplete knowledge was given for a first-order temporal policy language over logs with gaps by Basin, Klaedtke, Marinovic and Zălinescu [30], who prove that a definite evaluation is never retracted when the log is completed, and for a metric temporal logic with data values over out-of-order observations by Basin, Klaedtke and Zălinescu [31], who prove soundness with respect to every refinement and monotonicity. Both are approaches to monitoring; the theorems above are machine-checked counterparts for partial states, related to an enforcement decision. MonPoly [15, 16] monitors a safety fragment of metric first-order temporal logic (MFOTL), with quantification over data values and an interval on each temporal operator, and a monitor for that logic has been verified in Isabelle/HOL and exported as code [17], as the TRIEL evaluator is exported from theories in which its code equations are proved equal to the definitions. EnfGuard [29], which extends WhyEnf [32], enforces MFOTL with function applications, aggregations and let bindings proactively: it keeps a queue of obligations with deadlines, causes an event when a deadline risks being missed, and suppresses events; its soundness, and its transparency for a fragment, are proved in a technical report. Lex [33] translates rules that follow the structure of a statute into MFOTL and enforces them with EnfGuard [33, §1]; in its two-valued semantics an event predicate holds exactly when the event is in the database of the time point [33, §2.2.2], and facts that cannot be observed are settled by explicit assumptions [33, §5.3.1]. WhyMon [34] outputs an explanation of each MFOTL verdict, which a checker extracted from an Isabelle formalisation can check. The TRIEL core has fixed subjects, no quantification over data, no aggregation, deadlines of obligations and invariants resolved once, at activation, and a monitor that only suppresses a prohibited action at the top level of a `TERMS` block; its obligations are monitored, not enforced, and its report gives decisions without explanations.

## Formalisations in the Archive of Formal Proofs

- `LTL3_Semantics` [20] formalises the full logic LTL3 and formula progression. TRIEL has only `ALWAYS`, `EVENTUALLY`, `NEXT` and `EVENTUALLY … WITHIN` over a state formula, evaluated in strong Kleene logic on incomplete data.
- `MFOTL_Monitor` [21] and `MFODL_Monitor_Optimized` [22] verify executable monitors for metric first-order temporal and dynamic logic.
- `CondNormReasHOL` [23] embeds a dyadic deontic logic in HOL for conditional normative reasoning. TRIEL has no deontic inference; it gives verdicts on traces.
- `DCR-ExecutionEquivalence` [24] formalises the syntax and execution of DCR graphs.
- `Featherweight_OCL` [25] gives OCL a semantics with the values null and invalid besides true and false; `UPF` [26] models access-control policies as partial functions.
- `Extended_Finite_State_Machines` [27] contains a three-valued logic in which an invalid value absorbs both conjunction and disjunction (weak Kleene, or Bochvar, logic).

In a search of the AFP topics and keywords in October 2026 we found no entry that formalises strong Kleene logic over partial states.

## Information release in secure multiparty computation

In deployments of secure multiparty computation (MPC), the logic that decides which data may be released is often hand-coded. Skalka and Near [28] formalise noninterference and declassification for low-level MPC code. TRIEL works at the level of the specification: the information-flow rule for hidden zero-knowledge factors (`TECHNICAL_REPORT.md` §2.7) is checked on the specification by the translator to the formal core, and no report of the evaluator depends on the value of a hidden factor (`run_noninterference`). TRIEL does not define how a specification is implemented.
